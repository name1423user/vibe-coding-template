# 第6部 用語編

ここは引く辞書ではない。読める用語集として書く。
各用語を、これまでの章で実際に使った文脈のまま、一言で・もう少し詳しく・これが分かると何ができるか、の3段でまとめ直す。載っているのは、本文で実際に使い、判断に関わった用語だけだ。網羅は目的にしない。

## 開発の流れ

コードを書き、記録し、公開するまでの流れに関わる用語をまとめる。

### リポジトリ
**一言で**：Gitがコードの変更履歴を記録する場所。
**もう少し詳しく**：ある時点のコードの状態を記録する操作をコミットと呼び、その記録が積み重なる場所がリポジトリだ。リポジトリを見れば、いつ何を変更したかをたどれる。
**これが分かると**：Phase 4で最初のリポジトリを作る手順の意味が分かる。第1部1-5で触れた「戻せる」価値の置き場所が分かる。

### コミット
**一言で**：ある時点のコードの状態を記録する操作。
**もう少し詳しく**：動くことを確認した直後にコミットしておけば、次の変更で壊れても直前の状態に戻せる。原則2「常に動く状態を保つ」を実行する具体的な手段だ。
**これが分かると**：Phase 5以降、機能ごとにコミットする習慣の意味が分かる。

### 環境変数
**一言で**：コードの外側に置く設定値。
**もう少し詳しく**：パスワードやAPIキーのような秘密情報を、コードに直接書かず環境変数として扱う。値を変えるときにコードを書き換えずに済む。
**これが分かると**：Phase 4で秘密情報の置き場所を決める手順、第4部4-1の最低ラインが分かる。

### デプロイ
**一言で**：アプリをインターネット上で誰でも使える状態にする作業。
**もう少し詳しく**：ローカルで動くことと、公開して誰でも使える状態は別物だ。デプロイは、その間をつなぐ作業を指す。
**これが分かると**：Phase 8で公開する手順、第5部5-2で本番を直接触らない理由が分かる。

## アプリの構造

アプリを画面・処理・保存の3層に分けて捉えるときに使う用語をまとめる。

### フロントエンド
**一言で**：アプリの「画面」を担当する部分。
**もう少し詳しく**：利用者が実際に見て操作する部分を指す。処理を担当するバックエンド、保存を担当するデータベースと合わせて、アプリを3層で捉える。
**これが分かると**：Phase 3でフォルダ構成を決めるとき、どのファイルがどの層に属するかを判断できる。

### バックエンド
**一言で**：アプリの「処理」を担当する部分。
**もう少し詳しく**：画面から送られてきた内容を受け取り、計算したり判断したりする部分を指す。フロントエンドから届いたリクエストを受け取り、レスポンスを返す。
**これが分かると**：Phase 5で「画面→処理→保存」を1本通す実装の、真ん中の層が分かる。

### API
**一言で**：あるプログラムが別のプログラムの機能を呼び出すための窓口。
**もう少し詳しく**：外部のサービスを呼び出すときに使う。その窓口を使う権限を証明する文字列をAPIキーと呼び、これも秘密情報の一種になる。
**これが分かると**：Phase 4・第4部4-1で、秘密情報として何を環境変数に入れるべきかが分かる。

### データベース
**一言で**：データを整理して保存し、検索や更新をしやすくした保存先。
**もう少し詳しく**：メモリやファイルと違い、複数の利用者のデータを整理して管理できる。ReadLogのように、利用者ごとに複数のデータを登録し、後から検索・編集・削除する用途に向く。
**これが分かると**：Phase 3でデータ構造を表にするとき、どこに何を保存するかを決める土台になる。

### ライブラリ
**一言で**：他の開発者が作り、公開しているコードの部品。
**もう少し詳しく**：パスワードの安全な保存やデータベースへの接続処理を、一から自分で書く必要はない。借りて使うことができる。
**これが分かると**：Phase 4で必要なライブラリを導入する手順、第4部4-9で更新を確認する理由が分かる。

### 依存関係
**一言で**：自分のアプリがどのライブラリを、どのバージョンで使っているかという関係。
**もう少し詳しく**：自動では管理されない。記録しておかないと、別のパソコンで同じアプリを動かそうとしたときにライブラリが揃わず動かない。
**これが分かると**：第4部4-9で、依存関係の更新を確認する意味が分かる。

## 通信

フロントエンドとバックエンドがデータをやり取りする仕組みに関わる用語をまとめる。

### HTTP
**一言で**：インターネット上でデータをやり取りするときの共通の手順を定めた規格。
**もう少し詳しく**：フロントエンドとバックエンドは別々の場所で動いていることが多く、HTTPというやり取りの仕組みを通してデータを渡す。
**これが分かると**：第4部4-7で、公開するならHTTPS（暗号化されたHTTP）を使う理由が分かる。

### リクエスト／レスポンス
**一言で**：HTTPのやり取りを構成する2つの動き。
**もう少し詳しく**：フロントエンドから送る要求をリクエスト、バックエンドがそれに応えて返す内容をレスポンスと呼ぶ。
**これが分かると**：Phase 5で、画面から送った内容がどこに届くかを追えるようになる。

## 安全

第4部で扱った、セキュリティの最低ラインに関わる用語をまとめる。

### 認証
**一言で**：利用者が本人であることを確認する仕組み。
**もう少し詳しく**：パスワードを使った確認が代表例だ。パスワードは平文で保存せず、ハッシュ化して保存する。
**これが分かると**：第4部4-5の最低ラインと、Phase 4でパスワードをハッシュ化する理由が分かる。

### 認可
**一言で**：認証した利用者が何を行えるかを制御する仕組み。
**もう少し詳しく**：ログインしていれば誰の情報も見られる作りは、認可が抜けている状態だ。操作の対象が自分のデータかどうかを確認する処理がこれにあたる。
**これが分かると**：第4部4-6、Phase 6・7でReadLogの「他人の本が見えてしまう」不具合を直す理由が分かる。

### ハッシュ化
**一言で**：元の文字列を、逆算では元に戻せない別の文字列に変換する処理。
**もう少し詳しく**：パスワードをそのまま保存せず、ハッシュ化した値を保存する。データベースが漏れても、パスワードそのものは分からない。
**これが分かると**：Phase 4での実装、第4部4-5の最低ラインが分かる。

### 暗号化
**一言で**：データを第三者に読めない形に変換する処理。
**もう少し詳しく**：通信を暗号化するHTTPSが代表例だ。暗号化されていない通信は、途中で内容を読み取られる。
**これが分かると**：第4部4-7で、公開時にHTTPSを使う理由が分かる。

### 脆弱性
**一言で**：悪用されると被害につながるプログラムの欠陥。
**もう少し詳しく**：秘密情報の直書きやSQLインジェクションなど、第4部で扱う10項目は、脆弱性の中でも個人開発者が最初に潰すべき最低ラインだ。
**これが分かると**：第4部全体で、なぜ点検するかという前提が分かる。

### サニタイズ
**一言で**：危険な文字や構文を無害な形に変換する処理。
**もう少し詳しく**：入力された文字列をそのままHTMLに埋め込むと、悪意のあるスクリプトが実行されることがある。サニタイズは、この攻撃を防ぐ処理だ。
**これが分かると**：第4部4-4の最低ラインが分かる。

## AI関連

AIとの対話の質に関わる用語をまとめる。

### コンテキスト
**一言で**：AIが会話の中で参照できる範囲。
**もう少し詳しく**：コンテキストが長くなるほど、その中の古い部分の扱いが粗くなる。会話が長くなるとAIの精度が落ちるのは、これが理由だ。
**これが分かると**：第3部3-4で、会話を区切り直す判断基準が分かる。

### ハルシネーション
**一言で**：AIが事実でない内容を、事実であるかのように出力する現象。
**もう少し詳しく**：存在しないライブラリや関数を、実在するかのように示してくることが典型だ。公式ドキュメントに当てる、実際に動かすことで見抜ける。
**これが分かると**：第3部3-5で、AIの提案を鵜呑みにしない理由が分かる。

### プロンプト
**一言で**：AIに対して出す指示や質問の文章。
**もう少し詳しく**：文脈・目的・制約・出力形式の4要素で組み立てると、意図した答えが返ってきやすい。
**これが分かると**：第2部の各フェーズで使うプロンプト雛形、第3部3-1の4要素が分かる。
