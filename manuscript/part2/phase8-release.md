# Phase 8 リリースする

## このフェーズの目的

Phase 7までで動作と安全を確認したアプリを、実際にインターネット上に公開する。
公開して終わりではない。壊れたときに元の状態へ戻せることを、公開する前に確保しておく。ここまでの安全確認と同じく、事後対応ではなく事前準備として扱う。

## 成果物

- 公開されたアプリのURL
- 公開前の最終確認記録
- コードとデータを戻せる状態

## 手順

1. 公開先の選択肢を比較する。自分でサーバーを用意する方法と、アプリを預けて公開できる外部のホスティングサービスを使う方法がある。比較する軸（費用、設定の手間、公開を取り下げやすいかなど）は自分で決める
2. 比較した候補から公開先を決める
3. 公開前の最終確認をする。Phase 7で点検した秘密情報が、公開先の環境変数として正しく設定されているかを確認する。コードの中に値が残っていないかも合わせて確認する
4. 壊れたときに戻せる状態を作る。コードは直前のコミットに戻せる。データベースの中身は、コミットでは戻せないので別途バックアップしておく
5. デプロイする。デプロイとは、アプリをインターネット上で誰でも使える状態にする作業を指す
6. 公開後、実際にURLへアクセスして動作を確認する。このとき、URLが`https://`で始まっているかを確認する。Phase 7で持ち越した項目7（通信）は、ここで点検を終える。確認できたら、使ってほしい人にURLを共有する

ReadLogは、Phase 4で決めた環境変数（セッションの署名に使う値）を公開先の設定画面に登録し、コード側には残っていないことを確認したうえで公開した。

## AIへのプロンプト雛形

> 〇〇（技術スタック）で作ったアプリを公開する方法の候補を3つ挙げてください。それぞれの費用、設定の手間、公開を取り下げやすいかを比較してください。

公開先が決まったら、最終確認の手順を確認する。

> 公開前の最終確認として、環境変数が公開先に正しく設定されているか、コードの中に秘密情報が残っていないかを確認する手順を教えてください。

## 完了条件

- [ ] 公開先を比較して選んでいる
- [ ] 公開前の最終確認（秘密情報の混入なし）を終えている
- [ ] コードとデータの両方を戻せる状態にしている
- [ ] 公開後にURLへアクセスして動作確認している

## よくある失敗と戻り先

**公開してから秘密情報の設定を後回しにする**
公開先の環境変数を設定し忘れたままデプロイすると、アプリがエラーで起動しない。あるいは、設定を急いで済ませようとしてコードに秘密情報を直書きしたまま公開してしまう。Phase 7に戻り、点検をやり直してから公開し直す。

**戻せる状態を作らずに公開する**
公開後にデータが壊れても、バックアップがなく元に戻せない。Phase 8の手順4に戻り、戻せる状態を先に作ってからデプロイし直す。
