# Phase 3 設計する

## このフェーズの目的

このフェーズでは、データ構造・技術選定・フォルダ構成の3つを決める。
中心はデータ構造だ。ここを飛ばして実装に進むと、後から項目の型や必須・任意の扱いを変えることになり、画面と処理のコードを全部書き直す羽目になる。
技術選定とフォルダ構成は、データ構造が決まって初めて具体的に選べる。

## 成果物

- データ構造の表（項目名・型・必須かどうか）
- 技術選定の結果と、選んだ理由1行
- フォルダ構成案

## 手順

1. Phase 2で確定した機能一覧から、必要なデータの塊を洗い出す。ReadLogなら「ユーザー」と「本」の2つになる
2. 各データについて、項目名・型・必須かどうかの表を作る。ここを飛ばさない
3. 技術選定の候補をAIに3つ出させる。比較する軸（学習のしやすさ、情報量の多さ、公開のしやすさなど）は自分で決める
4. 候補から1つを選ぶ。選んだ理由を1行で書く
5. フォルダ構成を決める。画面・処理・保存の3層それぞれがどのフォルダに対応するかを明記する

ReadLogのデータ構造は次のとおり確定した。

| テーブル | 項目 | 型 | 必須 |
|---|---|---|---|
| users | id | 数値 | ○ |
| users | email | 文字列 | ○ |
| users | password_hash | 文字列 | ○ |
| users | created_at | 日時 | ○ |
| books | id | 数値 | ○ |
| books | user_id | 数値 | ○ |
| books | title | 文字列 | ○ |
| books | author | 文字列 | × |
| books | review | 文字列 | × |
| books | finished_on | 日付 | × |
| books | status | 文字列（未読／読書中／読了） | ○ |
| books | created_at | 日時 | ○ |

技術選定は「Node.js + Express + SQLite」「Python + Flask + SQLite」「PHP + ネイティブ」の3候補を比較し、学習のしやすさと情報量の多さを軸に選んだ。本書では以降、この構成で進める。

## AIへのプロンプト雛形

> このアプリで扱うデータを、項目名・型・必須かどうかの表にしてください。判断に迷った項目は指摘してください。
>
> 〇〇

技術選定には別のプロンプトを使う。

> 私はこのアプリを〇〇で作ろうと考えています。候補を3つ挙げ、それぞれの利点と欠点を示してください。比較の軸は「学習のしやすさ」「情報量の多さ」「公開のしやすさ」でお願いします。

## 完了条件

- [ ] どんなデータをどこに保存するか自分の言葉で説明できる
- [ ] 技術選定の候補3つを比較し、選んだ理由を1行で言える
- [ ] フォルダ構成を決めている

## よくある失敗と戻り先

**データ構造を決めずに実装から始める**
本の「感想を書いたかどうか」を後から区別したくなり、途中でデータの型を変えることになる。すでに動いている画面と処理をすべて書き直すことになり、Phase 5の作業量が跳ね上がる。Phase 3の手順2に戻り、表を作り直してから実装に進む。

**技術選定でAIの1つ目の提案をそのまま採用する**
比較軸を自分で決めずに「おすすめはどれですか」とだけ聞くと、AIが選んだ技術が自分の学習環境に合わないことがある。結果としてPhase 4の環境構築で詰まる。Phase 3の手順3に戻り、比較軸を自分で決め直してから選び直す。

**今は使わない列を省き、後で作り直すことになる**
「登録日時は今すぐ使わないから」と`created_at`のような列を表から省くと、後から「最近登録した順に並べたい」といった機能を思いついたときに、テーブルの構造を変えることになる。すでにあるデータに新しい列を追加する作業は、最初から入れておくより手間がかかる。Phase 3の手順2に戻り、今は使わなくても後で必要になりそうな列は先に入れておく。
