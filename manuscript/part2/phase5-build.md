# Phase 5 実装する

## このフェーズの目的

Phase 3で決めた最小構成の機能を、1つずつ動く形にしていく。
1機能を「画面→処理→保存」まで縦に1本通してから、次の機能に進む。原則1（小さく作る）と原則2（常に動く状態を保つ）を、実装の場面で実践する段階だ。
複数の機能を並行して作らない。並行させると、どこが壊れたかを切り分けられなくなる。

## 成果物

最小構成の機能がすべて動くコード。機能ごとのコミット履歴。

## 手順

1. 機能一覧から実装する順番を決める。土台になる機能を先に、それに依存する機能を後にする。ReadLogならログイン機能を最初に実装し、本の登録・一覧・詳細・編集・削除はその後にする
2. 1つの機能を選び、画面・処理・保存を1本通す最小の実装をAIに依頼する
3. 動かして確認する。原則2で決めたとおり、動くことを確認するまでは次に進まない
4. 動作を確認できたらコミットする
5. 次の機能に進む。依頼するときは、これまでに書いたコードをAIに見せる。何もない状態から依頼すると、既存の書き方と食い違うコードが返ってくる

ReadLogでログイン機能を実装するときは、Phase 3で決めた`users`テーブルとPhase 4で作った`src/routes/`を対象に、「メールアドレスとパスワードでログインできる」機能だけを依頼する。本の登録機能は含めない。

## よくある失敗と戻り先

**3機能まとめて頼み、どこが壊れたか分からなくなる**
「ログインと本の登録と一覧表示を作ってください」と一度に依頼すると、動かないときにどの機能の変更が原因か切り分けられない。原則1に立ち返り、Phase 5の手順1に戻って1機能ずつやり直す。

**既存コードを見せずに依頼し、書き方がバラバラになる**
機能ごとに命名や書き方が変わり、後から読み返したときに同じアプリのコードと思えなくなる。Phase 5の手順5に戻り、直前までのコードを見せてから依頼し直す。
