# Phase 定義（正本）

Phase の内容はこのファイルが唯一の正。原稿と食い違ったら原稿を直す。

| Phase | 名前 | 完了条件 |
|---|---|---|
| 0 | 壁打ちする | 作るものが1文で書ける |
| 1 | 決める | 1文で他人に伝わる／やらないことが3つ以上ある |
| 2 | 仕様を書く | 最初のバージョンの機能が5個以下に絞れている |
| 3 | 設計する | どんなデータをどこに保存するか自分の言葉で説明できる |
| 4 | 環境を作る | 空のアプリが起動し、コミットされている |
| 5 | 実装する | 最小構成の機能がすべて動く |
| 6 | 動作を確かめる | 正常系・異常系・極端な入力を試し終えている |
| 7 | 安全を点検する | 安全編10項目を通しで確認し終えている |
| 8 | リリースする | 公開され、壊れたときに戻せる状態がある |

## Phase 0 壁打ちする
作るものが決まっていない状態の入口。「何を作りたいか」ではなく「何が面倒か」から始める。
発散と収束を分ける。実現可能性（既存の類似物、個人の手に負える規模か）を早期に潰す。

## Phase 1 決める
作るものを1文で書く。やらないことリストを先に作る。誰がいつ使うかを1行ずつ。

## Phase 2 仕様を書く
画面の洗い出し。機能を「〜できる」の形で列挙。優先度3段階に分けて最小構成を確定。

## Phase 3 設計する
データ構造を先に決める（項目名・型・必須かどうかの表）。技術選定は候補3つと比較軸。フォルダ構成。
飛ばすと後で全部壊れる、と本文で明示する。

## Phase 4 環境を作る
Gitリポジトリと最初のコミット。「何もしないが起動はする」状態を先に作る。
秘密情報の置き場所（環境変数）をここで決め、`.gitignore` と `.env.example` を用意する。
脱落者が最も多い箇所。付録Dの詰まり対処に接続する。

## Phase 5 実装する
1機能ずつ、縦に薄く（画面→処理→保存を1本通す）。1機能ごとに動作確認とコミット。

## Phase 6 動作を確かめる
正常系／異常系／空・極端な入力。バグ報告の型（期待した動作・実際の動作・再現手順）。

## Phase 7 安全を点検する
安全編（第4部）の10項目を実際に通す。公開予定がなくても秘密情報の混入だけは必ず確認する。

## Phase 8 リリースする
公開先の選択肢と選び方。公開前の最終確認。戻せる状態の確保。公開後に最初にやること。
